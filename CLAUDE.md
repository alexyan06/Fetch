# Project: Fetch

Hackathon project for the Merge × Corgi hackathon (solo build, 12 hours). "Fetch" — the dog/Corgi tie-in, the literal act of fetching data, and the JS `fetch()` / `git fetch` double meaning.
Full research/planning detail lives in `/docs` — this file is the fast-load summary every session/worktree should start with. See the pointer table at the bottom for which `/docs` file to `view` for deeper context on a specific area.

## The core mechanic (don't drift from this)
Every company has a **coverage state** (current $ limit per coverage line) and a stream of **signal events**. When a new signal event arrives (from Merge for the real company, or from the generator/Simulate Event tool for everything else), the trained classifier scores it:
- **Below threshold (routine/small)** → compute a new limit via a simple scaling rule, update `coverage_state` immediately, log an `activity_log` entry tagged `auto`. This is the live demo moment — the Coverage Panel animates old value → new value.
- **At/above threshold (big/unusual)** → do NOT auto-act. Generate a written recommendation, create a `pending_approvals` row. Only a human clicking Approve applies the change (tagged `approved` in the log).

The 3 trigger events (straight from Corgi's own FAQ — use this exact framing, it's real primary-source language):
1. Hire the first non-founder employee → HRIS signal (`Employee.employment_status` = ACTIVE or PENDING with new `start_date` — PENDING counts immediately)
2. Raise a new funding round → Accounting signal (net inflow many multiples of normal monthly burn)
3. Sign a bigger enterprise contract → CRM signal (Opportunity closed-won, well above typical deal size)
(Tier 2 widens this to burn rate/runway and security-ticket-volume signals.)

**The Simulate Event tool is a required Tier 1 piece, not optional polish.** Synthetic companies have no real UI to edit, so an internal control (`/api/simulate-event`) fires a signal event on demand for any company. For the real company this also doubles as the live-demo backup if the actual BambooHR/Zoho Books/HubSpot path fails mid-demo. Dry-run mode (simulate the effect without touching Merge) is Tier 1; live-write mode (actually call Merge's Write API) is Tier 2 stretch. Full spec: `/docs/04-product-concept.md`.

**We never call or mock a real Corgi API.** The Coverage Panel, Activity Feed, and Pending Approvals queue are entirely our own UI, honestly presented as our tool's view — not a fake mockup of Corgi's actual dashboard.

## Confirmed stack — do not deviate without discussion
- **Next.js (TypeScript)**, single deploy unit, deployed on **Vercel**.
- **Tailwind + shadcn/ui** for UI. **Recharts** for charts.
- **Supabase (Postgres)** for the DB — using realtime subscriptions so the dashboard auto-updates when a trigger event lands, no polling.
- **Vercel AI SDK** (`ai` npm package) for the explainability chat feature.
- **ML**: train offline (scikit-learn), infer online in plain TypeScript. Do NOT deploy a live Python/scikit-learn runtime to Vercel — port the trained classifier's weights (logistic regression = weight vector + bias) into a small TS function instead. Anomaly detection = z-score/rolling-stats in TS, not isolation forest.
- **Merge Node SDK** for all Merge API calls.

## Hard guardrails
- **No real Corgi API exists** (confirmed via research) — do not attempt to call one. The "send to Corgi" action is a mocked confirmation or a deep-link to `corgi.insure/startup-insurance`. Use Corgi's real coverage-line names (CGL, D&O, Tech E&O, Cyber, EPLI, Media Liability, HNOA, Fiduciary, Rep & Warranties) for authenticity in mocked output.
- **Never claim this is a first-of-its-kind idea.** Vouch (Corgi's competitor) already shipped a narrower version (Carta integration, funding-round trigger only, recommend-only) in 2024. Our differentiation is breadth (multi-source via Merge), real automatic execution for safe cases, and a real trained model — not novelty of concept. This framing belongs in any UI copy/pitch text an agent generates.
- **The ML has to be real**, not an LLM call dressed up as ML. The classifier and anomaly detection are separate from the explainability chat agent — keep that distinction clear in code and in any generated copy.
- Secrets (Merge API key, Supabase connection string, LLM API key) go in Vercel env vars / gitignored `.env.local` — never hardcoded, never committed, never placed in `/docs`.
- **Data sources are NOT all Merge-backed.** Only ONE company (the real BambooHR/Zoho Books/HubSpot sandbox — all three now connected and validated with real data) goes through the real Merge pipeline. The other 15-19 portfolio companies are synthetic, generated by `ml/generate_training_data.py`'s approach and seeded directly into Supabase — they never touch Merge. Don't write code that assumes every company in the portfolio has a Merge account_token; branch on data source. See `/docs/05-technical-architecture.md` for the full split.

## Merge specifics agents need
- Test Linked Accounts, not full production OAuth flow, for the hackathon.
- Sandbox platforms: BambooHR (HRIS), Zoho Books (Accounting — swapped from QuickBooks, which didn't appear in the integration picker), HubSpot (CRM), Jira (Ticketing, Tier 2 only).
- Auth headers: `Authorization: Bearer <API_KEY>` + `X-Account-Token: <ACCOUNT_TOKEN>`.
- Relevant Common Models: HRIS `Employee`/`Employment`, Accounting `Transaction`/`CompanyInfo` (also check `CashFlowStatement.financing_activities` if populated — better funding-round signal than a derived ratio, see file 03), CRM `Opportunity`/`Deal`, Ticketing `Ticket`.
- Merge supports writing data too, not just reading — query `/meta` first to discover the exact required schema before POSTing (used by Simulate Event's live-write mode).
- Merge has its own MCP server (`merge-mcp`, separate from Agent Handler) — built on synced data, good fit for the Tier 2 explainability chat. Agent Handler is built for live real-time action-taking instead and is NOT part of current scope.
- If unsure of a field/endpoint shape, run `/merge-unified:integration-validator`, check `/docs/01-merge-product-technical-reference.md`, or fetch the live doc URL directly from `/docs/10-documentation-links.md` — don't guess.

## Build order (see `/docs/04-product-concept.md` for full tier detail, `/docs/11-hackathon-build-schedule.md` for the actual hour-by-hour plan)
**Event window: 10 hours, 8:00 PM – 6:00 AM, ~30 min break around midnight.** This is tighter than originally scoped — protect the schedule in file 11 over polishing any single piece past its checkpoint.
**Tier 1 (must work):** data model (`companies`, `coverage_state`, `signal_events`, `activity_log`, `pending_approvals`) → trigger detection across all 3 named events for 1 real + ~15-19 synthetic companies → classifier wired in → AUTO path (coverage update + feed entry) and PENDING path (recommendation + approval queue) both working → portfolio dashboard sorted by "needs attention" → company detail view (Coverage Panel + Activity Feed) → Simulate Event tool (dry-run mode) → full demo rehearsed end-to-end via both the real path and the Simulate Event fallback.
**Tier 2 (if ahead of schedule):** at most ONE addition given the shorter window — wider Merge categories OR explainability chat (via Merge's own MCP server), not both. Forward-looking projection and live-write Simulate Event mode are lower priority than either.
**Tier 3 (stretch only):** click-through audit trail per activity-log entry → "Send to Corgi" affordance → Merge Gateway routing for chat LLM calls.

Stop wherever the clock says stop. A complete Tier 1 beats a broken Tier 2. See file 11's "minimum viable Tier 1" section if running behind.
